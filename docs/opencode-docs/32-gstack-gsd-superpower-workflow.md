# GStack + GSD + Superpowers Workflow — объединение Spec-фреймворков

> **Источник:** Доклад Eric Tech  
> **Видео:** https://www.youtube.com/watch?v=BlTpG51x94w  
> **Стенограмма:** Авто-сгенерированная английская дорожка видео

---

Видео разбирает три популярных spec-first development фреймворка — **Superpower**, **G Stack**, **GSD** — и показывает, как объединить их лучшие стороны в единый workflow, а затем автоматизировать его через **Ralph Loop** и **Claude Headless**.

---

## Общая схема spec-first разработки

Все spec-фреймворки (SpecKit, B-Map, и любые другие) следуют одному и тому же циклу:

1. **Brainstorming** — прояснение того, что вы строите
2. **Planning** — как именно выполнять: таск-листы, разбивка на фазы
3. **Execution** — реализация
4. **Review / Verification** — проверка, возможно через Playwright или другой browser agent

Разница между фреймворками — в том, на чём сделан акцент.

---

## Три фреймворка

### Superpower

**Акцент: Test-Driven Development (TDD)**

Пишет тесты до реализации. Используется на этапе **execution** как основной исполнительный движок.

### G Stack

**Акцент: Role-based принятие решений**

Симулирует разные роли (CEO, дизайнер, engineer manager, security manager) для голосования и выбора лучшего решения. Используется на этапе **brainstorming / planning** для прояснения требований и генерации spec.

### GSD (GPT Spec-Driven)

**Акцент: борьба с context rot**

Context rot — проблема, при которой точность LLM падает после заполнения ~50% контекстного окна. GSD решает это разбиением spec на **фазы**, каждая из которых выполняется в **отдельной сессии с чистым контекстом**.

---

## Комбинированный workflow

Автор предлагает взять лучшее из каждого фреймворка:

```
G Stack    → Brainstorming / прояснение intent, создание spec
GSD        → Разбивка spec на фазы (чтобы избежать context rot)
Superpower → TDD-execution для каждой фазы
```

### Для greenfield проектов (с нуля)

Используется полный комбинированный подход: G Stack → GSD → Superpower.

### Для brownfield проектов (существующий код)

Достаточно одного фреймворка:
- Superpower для добавления отдельных фич
- G Stack + Superpower для полу-крупных проектов

## Автоматизация через Build Loop и Ralph Loop

Если фаз 7–8+ и больше, запускать каждую вручную через новую сессию — трудозатратно. Для этого создан **Build Loop** — skill на основе Ralph Loop, который:

1. Хранит все промты для каждой фазы в одном state-файле
2. Использует **Claude Headless** (`claude -p <prompt>`) для запуска каждой фазы в фоне
3. Оркестратор отслеживает completed-статус и запускает следующую фазу
4. Каждая headless-сессия имеет **свежий чистый контекст**
5. Основной оркестратор не засоряет свой контекст деталями execution

### Результат из демо

- **16 из 16 фаз завершено** за ночь
- **>100 headless-сессий** в фоне
- Контекст основного оркестратора — всего **10%**

### Декомпозиция архитектуры

```
┌─────────────────────────────────┐
│  Claude-сессия (оркестратор)    │  ← контекст ~10%
│  ┌───────────────────────────┐  │
│  │  Work Scheduler           │  │
│  │  (Build Loop / Ralph Loop)│  │
│  └──────────┬────────────────┘  │
└─────────────┼───────────────────┘
              │ делегирует фазы
    ┌─────────┴─────────┐
    ▼                   ▼
┌─────────────┐   ┌─────────────┐
│ Headless #1 │   │ Headless #2 │  ← свежий контекст
│ Superpower  │   │ Superpower  │
│ TDD-цикл    │   │ TDD-цикл    │
└──────┬──────┘   └──────┬──────┘
       │                 │
       ▼                 ▼
  ┌──────────┐     ┌──────────┐
  │ G Stack  │     │ G Stack  │  ← принятие решений
  │ (вотум)  │     │ (вотум)  │
  └──────────┘     └──────────┘
```

### Как работает принятие решений

Если Superpower (execution) сталкивается с архитектурным вопросом:
1. Он триггерит G Stack
2. G Stack запускает голосование ролей (CEO, дизайнер, инженер)
3. Выбирается самый популярный вариант
4. Управление возвращается в основной поток
5. Человек не участвует

---

## Итог

| Фреймворк | Роль |
|-----------|------|
| **G Stack** | Brainstorming, прояснение intent, создание spec, принятие решений |
| **GSD** | Разбивка spec на фазы, борьба с context rot |
| **Superpower** | TDD-ориентированное исполнение каждой фазы |
| **Ralph Loop** | Автоматизация цикла: оркестратор → headless-сессии |

**Ключевой принцип:** каждая фаза выполняется в отдельном headless-сессии Claude с чистым контекстом. Оркестратор только делегирует и собирает результаты, оставаясь в ~10% контекстного окна.

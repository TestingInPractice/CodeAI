# Development Process для сложных OpenCode-проектов

**Глава 08**

---

## Главный принцип

Сложный проект не должен развиваться как один бесконечный прогон генерации кода. OpenCode должен работать внутри понятного контура: исследование и план → ограниченный инкремент → верификация → review → фиксация.

## Operating model проекта

| Этап | Что происходит | Артефакт на выходе |
|------|---------------|-------------------|
| **Explore / Plan** | Изучение кодовой базы, ограничений, похожих участков | План действий, риски, assumptions |
| **Implement** | Минимальный рабочий инкремент в строгом scope | Понятный diff без побочных изменений |
| **Verify** | Lint, typecheck, тесты, smoke | Статус проверок |
| **Review** | Read-only проход по изменениям | Находки, open questions |
| **Report** | Stage notes | Что сделано, что осталось, next step |

## Стартовая настройка

### AGENTS.md как проектный контракт

- Как собрать проект и запускать локальную среду
- Как запускать тесты, линтеры, typecheck
- Критичные пакеты, сервисы, директории
- Архитектурные слои
- Запрещённые паттерны
- Что проверить перед завершением задачи

### Permissions как boundary контроля

| Инструмент | Режим | Комментарий |
|-----------|-------|-------------|
| `read`, `grep`, `glob`, `list` | **allow** | Базовый контур должен быть дешёвым |
| `edit`, `write`, `apply_patch` | **allow** в build | Там, где изменения ожидаемы |
| `bash` | **ask** или узкий allow-list | Лучше явно контролировать |
| Deploy, cloud, DB | **approval only** | Отдельный инфра-контур |

## Как дробить работу

**Плохо:** «сделай весь backend» — scope не наблюдаем, риски скрыты.

**Хорошо:** вертикальный delivery slice — пользовательский сценарий, capability, интеграционный шаг.

## Один управляемый рабочий цикл

### 1. Plan

С контекстом, ограничениями, ссылками на код, критериями приемки. На выходе — план, а не код.

### 2. Уточнение плана

«Какой минимальный инкремент закрывает основной риск и даёт демонстрируемый результат?»

### 3. Build

Ровно согласованный scope, без дополнительных «улучшений».

### 4. Verify

Агент запускает команды и сообщает статус честно. Никаких «предположительно всё ок».

### 5. Review

Поиск архитектурного drift, лишней сложности, побочных эффектов, missing tests.

### 6. Stage Notes

Короткий отчёт: что сделано, что изменено архитектурно, риски, manual QA, следующий шаг.

## Моноагент или мультиагенты

### Когда достаточно моноагента

- Задача обозрима внутри одного planning loop
- Контекст помещается в один reasoning cycle
- Архитектура ясна

### Когда переходить к мультиагентам

- Проект слишком велик для одного контекста
- Frontend, backend, infra смешиваются в шум
- Нужен независимый review или параллельная работа

### Практичная схема ролей

| Роль | Задача |
|------|--------|
| **Planner** | Декомпозиция, план, assumptions, риски |
| **Build** | Реализация scope, подготовка diff |
| **Review** | Read-only code review |
| **Debug** | Расследование дефектов |
| **Docs** | Release notes, ADR, runbooks |
| **Infra** | IaC, CI/CD, rollout (отдельный permission-контур) |

## Как управлять качеством кода

**Done — это не «код написан»:**
- Код закрывает заявленный сценарий
- Статические проверки и тесты пройдены
- Контракты и решения задокументированы
- Риски и ограничения перечислены

### Second pass review обязателен

Поиск: побочные эффекты, архитектурный drift, избыточная сложность, уязвимости, пропущенные тесты.

## Универсальный operating model

### На уровне проекта

- Один backlog, короткие этапы
- Единый Definition of Done
- Обязательный AGENTS.md
- Skills для типовых процедур
- Build, verify, review — отдельные фазы

### На уровне задачи

1. Plan → 2. Build → 3. Verify → 4. Review → 5. Document

### На уровне релиза

- Changelog / release notes
- Список ручных проверок
- Known issues
- Rollout plan + Rollback plan
- Post-release monitoring

## Антипаттерны

- Большое ТЗ → один длинный прогон
- Сначала весь backend, потом весь frontend
- «Ревью не нужно, агент уже написал»
- «Потом допишем тесты»
- AGENTS.md не нужен
- Чем больше агентов, тем лучше

## Минимальный золотой стандарт

1. Всегда начинайте крупную задачу с `plan`
2. Фиксируйте правила в `AGENTS.md` и коммитьте
3. Дробите работу на маленькие этапы
4. Держите permissions под контролем
5. Разделяйте роли: plan, build, review, debug, docs
6. После каждого этапа — верификация и stage notes
7. Не путайте скорость генерации со зрелостью инженерного процесса
